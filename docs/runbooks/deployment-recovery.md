# Deployment and recovery runbook

Owner: platform maintainer. This runbook applies only after the GitHub `nonprod` and `production` environments, the listed AWS OIDC roles, and repository variables have been explicitly bootstrapped and verified by T010/T032.

## Required configuration

Set repository variables, never secrets, for the approved region, the environment-specific OIDC role ARN, ECR registry and API/worker repositories, ECS cluster and API/worker service/task-definition/container names, the dedicated migration task definition/container, HTTPS health URL, and Cognito identifiers. Set the protected environment secrets `AWS_<ENV>_COGNITO_OWNER_USERNAME` and `AWS_<ENV>_COGNITO_OWNER_PASSWORD`; they are used only to obtain an ID token for `/ready` and are never printed. Non-production requires `AWS_REGION`, `AWS_NONPROD_ROLE_ARN`, `AWS_NONPROD_ECR_REGISTRY`, `AWS_NONPROD_API_REPOSITORY`, `AWS_NONPROD_WORKER_REPOSITORY`, `AWS_NONPROD_ECS_CLUSTER`, `AWS_NONPROD_ECS_SERVICE`, `AWS_NONPROD_ECS_TASK_DEFINITION`, `AWS_NONPROD_ECS_API_CONTAINER`, `AWS_NONPROD_WORKER_SERVICE`, `AWS_NONPROD_DATABASE_INSTANCE`, `AWS_NONPROD_WORKER_TASK_DEFINITION`, `AWS_NONPROD_ECS_WORKER_CONTAINER`, `AWS_NONPROD_MIGRATION_TASK_DEFINITION`, `AWS_NONPROD_ECS_MIGRATION_CONTAINER`, `AWS_NONPROD_HEALTH_URL`, `AWS_NONPROD_COGNITO_AUTHORITY`, and `AWS_NONPROD_COGNITO_CLIENT_ID`. Production uses the corresponding `AWS_PRODUCTION_*` names.

Production uses the same names with `NONPROD` replaced by `PRODUCTION`, except the shared `AWS_REGION`. A production rollback additionally requires the exact API and worker task-definition ARNs from one retained successful production-promotion record.

The API and worker task definitions must both provide `Ingest__Database__Host`, `Ingest__Database__Port`, `Ingest__Database__Name`, restricted runtime `Ingest__Database__Username`/`Password` secrets, `Ingest__Bucket`, and `Ingest__KmsKeyId`. A separate migration task receives the RDS administrator secret plus `Ingest__RuntimeDatabase__Username`/`Password`; it alone applies schema changes and provisions or rotates the runtime role with application-table DML and sequence access but no migration-ledger or schema authority. Each process assembles its TLS-required connection string only in memory. The bucket must be private, versioned, and encrypted with the named KMS key. API writes are limited to `staging/*`; worker writes are limited to `sha256/*` and `quarantine/*`. Only the worker may remove staging/quarantine versions, while both roles explicitly deny deletion of authoritative `sha256/*` versions. The worker service supplies the Fargate network configuration used by the one-off migration task. Grant the deployment role narrow ECR operations for both repositories, ECS describe/register/run/update permissions for the named cluster, tasks, and services, scoped `ecs:StopTask` for interrupted migrations, and `iam:PassRole` only for the named task and execution roles.

Configure the web artifact's same-origin `/platform-config.js` at deployment with `window.__PLATFORM_CONFIG__ = { apiBaseUrl, cognitoHostedUiUrl, cognitoClientId, redirectUri }`. `webOrigin` and a globally unique `cognitoDomainPrefix` are mandatory CDK context inputs at bootstrap; use the same `webOrigin` as the Cognito callback/logout origin. These runtime values are environment configuration and must not be baked into the immutable web artifact.

For each environment, inject `Authentication__CognitoAuthority` and `Authentication__CognitoClientId` into the ECS API task definition from that environment's Cognito user-pool issuer and web-client ID. They are public identifiers, not secrets, but must be supplied as versioned deployment configuration and recorded with the deployment evidence. The API fails owner requests closed when they are absent or invalid; never substitute a static token.

The roles must trust only this repository, the intended workflow/environment, and the GitHub Actions audience. Grant only ECR push/pull and the named ECS task-definition/service operations required by the corresponding workflow. Do not add static AWS keys or place runtime configuration in the manifest.

## Normal delivery

1. Merge a revision into protected `master` after `ci / required` succeeds. `Build release evidence` creates the five locked build artifacts, checksums, SPDX SBOM, a run-bound in-toto/SLSA provenance statement, CI-validation record, and release manifest for that exact SHA. The manifest verifier requires the provenance subjects, source SHA, triggering CI run, builder workflow, and release-workflow invocation to match before deployment.
2. `Deploy non-production` verifies every manifest digest, starts or waits for the non-production RDS instance, refreshes its OIDC credentials, publishes the API and ingest-worker images by registry digest, checks the runtime and migration task definitions for required ingest configuration, runs the checksum-pinned additive migrations as the dedicated one-off migration task, and updates both ECS services. Refreshing after the potentially 25-minute database start gives deployment and rollback a new one-hour role session. A migration timeout or signal stops the remote task and waits for it to finish. The deployment then requires service stability, public `/live`, authenticated `/ready`, and a one-item import/download/delete/restore/manifest smoke test. A failed service or smoke gate restores both prior task definitions; additive schema remains for forward recovery. The database can remain running after failure until the daily or manual shutdown.
3. Create a `v*` tag pointing to that validated `master` SHA. `Promote production release` pauses at the protected `production` environment approval, verifies the tag ancestry plus the paired non-production API/worker/migration/smoke evidence, then runs the same coordinated migration and two-service deployment path. It records both artifact checksums, image digests, task definitions, prior rollback targets, tag, smoke result, and approval-protected workflow run.

Abort immediately if any digest check, OIDC role assumption, ECS stability wait, or health probe fails. Do not rerun against a different revision or rebuild an artifact to bypass a failed gate.

## Non-production lifecycle and cost recovery

`Manage non-production lifecycle` uses the same protected environment, OIDC role, and `deploy-nonprod` concurrency group as deployment. Manual `start` waits for RDS before setting the latest API and worker task definitions to desired count one, then restores version-control missing-heartbeat notifications after ECS is stable. Manual `stop`, and the daily `17:00 UTC` schedule, set the API to zero, suppress that alarm's actions, set the worker to zero, wait, and stop RDS. A successful deployment also restores heartbeat notifications. Each run reports the final database and desired-count state. Manual start is valid only after the initial release has registered runnable images.

If start fails, keep both services stopped, inspect the reported RDS state and CloudFormation events, and retry after the transient state clears. If services are running after a failed start or deployment, run `aws cloudwatch enable-alarm-actions --alarm-names "$AWS_NONPROD_VERSION_CONTROL_HEARTBEAT_ALARM"`. If stop fails before the database request, verify both desired counts are zero and rerun stop; keep heartbeat notifications suppressed while the API desired count is zero. If it fails after the database request, inspect `describe-db-instances`; `stopping` can be safely waited and `stopped` is success. Do not delete the retained database to reduce cost. AWS automatically starts an RDS instance after seven stopped days, so a failed daily workflow needs prompt investigation.

Live Singapore rates reviewed on 2026-09-13 put RDS plus two ECS tasks at about USD 0.056 per active hour, with additional storage, KMS, secrets, logs, API, and request costs. Limit active compute to about 40 hours/month and retain the USD 20 budget alerts. The alert is not a spending cap.

## Failed deployment and rollback

If a production health or smoke probe fails, the promotion workflow restores both captured prior task definitions before it reports failure; keep the failed task definitions and workflow log as incident evidence. For a later operator-initiated rollback, identify the latest healthy retained `production-promotion-evidence` workflow run whose manifest has `compatibility.rollbackAllowed: true`. Start `Roll back compatible production release` with that production-promotion run ID, both exact task-definition ARNs recorded in its `production-promotion.json`, and an incident reference. The protected production approval is required again. The workflow verifies both artifact checksums, compatibility, and exact evidence-to-task-definition bindings before it updates both ECS services, waits for stability, re-reads each service to require the requested task-definition ARN, and reruns liveness, owner readiness, and the ingest smoke. A circuit-breaker reversion to the current or a previous task definition is a failed rollback even if that release is healthy.

Rollback is refused when the manifest is missing, checksum verification fails, compatibility is false, the target is unnamed, or health fails. In that case use an approved forward-recovery plan: contain traffic, preserve the persistent state and evidence, prepare an expand/migrate/contract-compatible corrective release, obtain production approval, and record the data-reconciliation result. Never report persistent state as rolled back merely because application tasks were restored.

## Time and escalation thresholds

The non-production deployment job is bounded at 90 minutes: cold RDS startup is capped at 25 minutes, the coordinated deployment script at 35 minutes, and at least 30 minutes remain for setup overhead and paired rollback. Migration and service-stability waits are each capped at 10 minutes and the ingest smoke at 2 minutes. Production deployment remains bounded at 60 minutes with a 25-minute reserve after its 35-minute deployment script. The standalone rollback job is bounded at 40 minutes and its mutation script at 20 minutes, preserving another 20 minutes to restore the captured current pair after a late failure. Escalate to the platform maintainer immediately for failed OIDC, evidence mismatch, an unavailable prior healthy task definition, an unexpected post-wait task definition, or any health failure lasting five minutes after ECS reports stable. Treat leaked credentials or a manifest/artifact mismatch as a security incident; stop deployment and rotate/revoke through the credential-compromise runbook when it is published in T028.
