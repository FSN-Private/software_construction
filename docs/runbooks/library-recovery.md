# Library backup and recovery

**Status:** local software and templates are implemented and under validation. No AWS recovery account has been deployed or qualified. Do not treat a successful local test or an unconfigured workflow as recovery evidence.

## Recovery boundaries

The primary capture task runs in ap-southeast-1 every 15 minutes. It takes a PostgreSQL 18 exported MVCC snapshot, runs `pg_dump` against that same snapshot, and writes a sealed inventory/configuration capture to the primary capture bucket. It uses the independently provisioned, read-only database secret. The recovery account in ap-southeast-2 polls every 5 minutes, assumes the primary read role only while copying, verifies exact source versions and bytes, records recovery-owned write intents, then advances the verified-point watermark only after the joined database and object point is complete.

Protected payload and snapshot copies are versioned, SSE-KMS encrypted, Object Lock governance-retained for at least 90 days, and never expire automatically. Only `payload/` objects move to Glacier Instant Retrieval after 90 days; database dumps under `snapshots/`, manifests, release artifacts, configuration, audit and evidence remain in Standard. The payload bucket's default retention starts when an object version arrives, while logical purge eligibility is measured from the signed proposal and lifecycle state. Those clocks can differ: an exact version can remain locked beyond its logical eligibility time. The purge executor must stop and report that version as pending until S3 permits deletion; never shorten or bypass governance retention. A separate mutable target bucket receives verified bytes under `sha256/{digest}` during isolated restore. The recovered API has permission to that target bucket only; it has no access to the protected payload bucket or primary account. No native S3 replication is enabled because asynchronous replicas can outlive purge writer fencing.

Copy/checkpoint evidence and MFA owner-approval receipts use separate RSA-PSS-SHA256 KMS keys. The recovery worker can sign recovery evidence but cannot sign approvals. Only the separately provisioned MFA owner role can sign the owner-approval key. The API and worker verify approval receipts against an SPKI/fingerprint pin delivered through recovery configuration, never a key embedded in a receipt. The recovery API resolves the new Cognito issuer, audience and subject through the signed server-side binding to the preserved logical owner ID; clients cannot submit an owner ID. A separate, manually invoked ControlTable index-bootstrap task has its own role limited to strongly consistent inventory/index reads and writes; it receives no primary, object-store, evidence, database, signer, or fence access.

## Monitoring and alert response

The capture, copy and drill tasks emit one-line CloudWatch Embedded Metric Format events to their existing encrypted ECS log group. The metrics use only `Environment` and fixed `WorkerId` dimensions. CloudWatch Logs extracts the metrics from the log events; task roles do not receive `cloudwatch:PutMetricData`.

| Metric/alarm | Limit | Response |
|---|---:|---|
| `VerifiedPointAgeSeconds` | 2,700 seconds (45 minutes) | Treat as unhealthy. Check capture completion, source-reader grants, copy role assumption, pending write intents, destination access, signatures, object retention/access, database/object closure and KMS availability. Do not advance the watermark manually. |
| `RecoveryWorkerHeartbeat` (`WorkerId=copy`) | One successful copy/freshness cycle per 5-minute period | Treat missing data as a breach. Check EventBridge target status, ECS task exit reason, log ingestion and EMF parsing metrics. |
| `RecoveryWorkerHeartbeat` (`WorkerId=capture`) | Three consecutive 5-minute periods without a successful capture | Treat missing data as a breach. Check scheduled capture task, database reader secret, database reachability, scratch storage and dump/upload outcome. |
| `CopyFailures`, `VerificationFailures`, `CaptureFailures` | Any emitted failure | Preserve the signed error observation. Keep the last verified point unchanged; repair and resume by idempotent exact-version receipts. |

The age alarm's 45-minute threshold leaves at most 15 minutes to detect and deliver an alert before the 60-minute RPO boundary. The heartbeat, SNS acceptance and actual email delivery must be measured in a drill; CloudWatch configuration alone does not prove the 15-minute notification objective. A missing point uses the worker's explicit over-threshold sentinel, never a fabricated current timestamp or age of zero. AWS EMF extraction is asynchronous and at-least-once; investigate parsing/validation errors in the `AWS/Logs` namespace and account for duplicate values in failure/heartbeat metrics. See [AWS EMF guidance](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch_Embedded_Metric_Format.html).

## Restore, promotion and purge

Local purge implementation now retains immutable per-version admissions/results in the recovery FenceTable. A lost provider response remains pending until exact-version absence is confirmed; restart authenticates the original plan and reuses confirmed receipts without renewing timestamps. Private proposal/approval files are limited to 64 KiB and plans to 64 MiB before allocation. The approved [completion protocol](../features/011-backup-disaster-recovery/reviews/purge-completion-proposal.md) is still being implemented: snapshot preservation, permanent old-point exclusions, explicit MFA renewal, complete target cleanup and independent hold/fence release are required before normal generated plans can execute. The current snapshot-preservation guard remains in place; journal unit evidence is not proof of completed purge or AWS qualification.

Routine verification authenticates an exact checkpoint's private `FULL_VERIFY` proof before reusing its original full-read time for up to 24 hours. It still checks exact versions, length, current provider locks and one-byte access. Expired proof evidence forces a complete media rehash. Without a proof, signed-copy receipt timestamps govern the same deadline; any due or legacy media receipt forces the entire closure to be read before a proof is signed. Fresh copy receipts permit ordinary checks without creating a proof. New copy checkpoints cannot inherit another checkpoint's proof. Failed full reads produce no proof, and a write retry does not refresh the original read time. Drills always read full media. These records stay in the recovery account and grant no health, hold-release, promotion or purge authority.

For accidental loss, select a fully verified point before the reported change and use a new isolated restore session. Never overwrite the live database or target bucket during validation. Verify that the target point, database graph and exact recovery payload closure agree, and inspect all holds and purge/write-intent fences. A human owner must approve a plan-bound promotion with a fresh recovery MFA identity after validation and generation checks. Keep the previous live generation available for reviewed rollback.

The local worker now exposes `recovery-worker restore <canonical-proposal.json>`. The private v1 proposal contains schema version, session/point IDs, owner/library, requested full-library/asset/edit scope, request digest and the original expiry (at most 24 hours). It must match the configured recovery owner/library; it is a retrieval request, not promotion authority. Use the existing independently pinned recovery-only configuration and selected point's matching release artifacts. The command authenticates the compact catalog, indexed checkpoint, full media closure and independent audit proof before restoring pinned schema/data into `recovery_drill_<session-without-hyphens>_<point-first-eight>`. It retains the clone, rebinds exact target versions and records immutable validation revisions. It does not launch normal access or qualify access to that clone. The final state remains `validating`, with owner access pending.

Retries must preserve the exact proposal, expiry, point and runtime binding. A private signed request at `evidence/restores/<session>/request.v1.json` prevents rebinding the session. A database advisory lock excludes concurrent executors. Existing clones must contain the exact immutable request before retry mutation; an interrupted schema import without that binding returns `restore_clone_reconciliation_required` and is preserved for exact operator reconciliation. No retry overwrites or drops a clone. Expiry cancels retrieval and later writes; provider-unknown materialization remains subject to the existing durable intent protocol. Full orchestration fault tests and fresh clone-access/promotion wiring remain tracked in T029; this command is not production qualification.

For regional loss, do not use the primary AWS role or a primary-region endpoint. Recreate the recovery app and configuration from the pinned recovery image repositories and database/config snapshots. Authenticate to the recovery Cognito pool over the supported private path, enroll/verify MFA, and create only an independently approved signed issuer/audience/subject-to-preserved-owner binding. Do not overwrite historical graph rows or accept caller-selected owner IDs. Do not automatically reverse-replicate when primary returns; reconcile and cut over through a separate reviewed operation.

Purge means approved media payload deletion only. The approved design retains immutable historical graph rows, hashes, paths, audit records and descriptive metadata in recovery database snapshots; disclose that paths and metadata can remain. Before approval, enumerate active holds, shared content, source and recovery exact versions, pending/unknown write intents, multipart uploads, cold objects and Feature 012 export intents. Require recovery-side fresh hold validation and a signature over the exact scope and plan digest. Do not complete purge until source deletion, recovery deletion, durable export cleanup acknowledgement and provider settlement are independently verified. Routine retirement must preserve the final verified copy. An independently approved, eligible media-only purge may remove its exact final payload copy, but must preserve unrelated protected content and metadata. Never bypass Object Lock governance. Full metadata erasure needs a separately approved graph-redaction design.

The infrastructure defines a separate purge-executor role trusted only from the configured recovery-account MFA operator principal. The user approved this exact local IAM definition on 2026-10-06. It can read owner-point/control and write-intent records; create/update recovery fences; delete fence items only in `SNAPSHOT#*` partitions; list and read exact versions only under `payload/sha256/*` and `snapshots/*`; read `points/*` evidence versions; and delete exact payload/snapshot versions. KMS decrypt is limited to the two recovery storage keys, through regional S3, and to those object-prefix encryption contexts. It has no primary-account, database-secret, owner-approval-key, evidence-signing, evidence-delete, or intent-write access. The application must condition snapshot-fence release on the exact authorized sentinel and signed completion. The approval covers local template code and tests only; it does not authorize deployment, assuming the role, or deleting AWS objects.

### Independent recovery-hold release

With the existing independently pinned verifier configuration, select the historical point with `Recovery__RecoveryPointId` and run `recovery-worker hold-release <owner-signed-approval> <private-proof-output>`. The canonical approval binds the exact captured hold ID/definition, creation UTC, owner/library, independent MFA identity and a validity window of at most 15 minutes. The owner approval key must differ from the recovery signing key. The worker fully verifies the exact point's media, release, pinned native schema/data, graph and audit before conditionally retaining its private `HOLD_RELEASE` proof in VerificationTable. An exact retry preserves the original proof bytes and recovery-observed UTC, including after approval expiry; changed approvals cannot replace that proof. Output is a create-new private file; never send it to the primary observation queue.

Supply exported proof paths to the purge executor as the JSON array in `Recovery__HoldReleaseEvidenceFiles` (at most 256 files, each at most 64 KiB). Every included proof is independently signature checked and bound to captured checkpoint/hold history. Missing evidence keeps protection active; primary row deletion or `released_at_utc` cannot release a recovery hold. Later active observations or changed definitions prevent eligibility. The 90-day obligation starts at the original recovery-observed release UTC, not a backdated owner/primary timestamp. Hold release grants no purge, promotion or healthy-backup authority. The existing snapshot-preservation guard still prevents normal purge completion pending T034.

For `kind=lifecycle`, select the earliest indexed snapshot containing the exact hold definition. Supply `Recovery__HoldHistoryBindingsFile`: a private JSON array of `{ "pointId": "<UUID>", "pins": { ... } }` entries covering every indexed owner point. Each `pins` object contains exactly `ConfigurationDigest`, `ApiBuildDigest`, `SourceRevision`, `MigrationDigest`, `RecoveryWorkerBuildDigest`, `RecoveryTemplateDigest`, `SourceTemplateDigest`, `OwnerUserPoolId`, `OwnerUserPoolClientId`, `OwnerUserPoolIssuer`, `MigrationDirectory`, `IngestWorkerBuildDigest`, `RendererBuildDigest`, and `DatabaseRootCertificateSha256`. These are explicit historical release expectations and the local directory containing that release's exact migration artifacts. The source certificate digest describes archived source configuration; current recovery database TLS trust and credentials are unchanged. The file is bounded to 64 MiB and 65,536 distinct points; it grants no authority by itself. Credentials, accounts, owner/library and trust keys always come from the existing independently controlled runtime configuration, and cannot be overridden in `pins`.

The command uses existing authorized `GetItem` reads only: every distinct supplied point must be an exact member of the configured owner partition, and the complete set must match the strongly read index count. Checkpoints/manifests, independently owner-signed historical access proofs and exact release/configuration artifacts must match each supplied release expectation. It authenticates every exact dump, extracts the hold history, and rechecks the complete index/pointers before retaining a proof. The selected earliest point receives native graph/audit validation against its own exact pinned migration directory; this supports pre/post-025 history without treating current schema as authority for an old dump. ### Retained snapshot preservation evidence

These per-point release bindings currently support lifecycle proof production. The complete cross-release purge-consumption and snapshot-exclusion workflow remains unfinished under T034/T035; possession of a lifecycle proof does not complete that workflow.

Run `recovery-worker snapshot-proof <private-proof-output>` with the separately pinned verifier configuration and `Recovery__RecoveryPointId` set to the exact indexed point. The worker verifies all exact media bytes, release bindings, historical owner-access evidence and audit-head proof, then reconstructs the dump using only pinned schema and authenticated COPY data. It compares the complete schema/column/type inventory with the trusted pre-import inventory and refuses PostgreSQL large objects. Media classification is limited to the current v1 migration set's explicitly pinned, line-ending-normalized digest; any migration change requires classification review before signing. The original migration-byte digest is still verified separately and included in the proof.

Known schema alone does not classify stored binary values. The producer authenticates global audit evidence and validates canonical commit bytes for every owner/library in the retained dump. It conservatively refuses any non-null value in other binary evidence columns until a bounded typed value validator is implemented. This currently includes populated recovery catalog/observation, identity and purge evidence blobs; snapshots containing them remain protected and unqualified for media-free preservation. No unparsed payload-bearing row receives a proof merely because its count or byte length matches coverage. Additional binary value validators remain T034 work.

The private, canonical `recovery_snapshot_media_free` envelope binds point/capture, owner/library, checkpoint/source manifest, exact retained dump bucket/key/version/hash/length, migration/schema/validation digests, verification UTC and worker digest. The output file is create-new and contains private physical locators; retain it only through the approved operator handoff. The command neither publishes this proof to the primary queue nor deletes any dump or media. Purge proof consumption, complete exclusion overlays and final completion remain T034 work; a preservation proof alone cannot remove the existing snapshot-deletion guard or qualify an old point for normal restoration.

## Cost and recovery envelope

Unchanged media reuse now extends an insufficient GOVERNANCE lock on the same exact `payload/sha256/<digest>` version to recovery UTC now plus 91 days, only after existing authenticated receipt/fenced admission/access checks. The copy-role permission is bounded to 90–92 remaining days and grants no governance bypass, shortening, legal hold or snapshot/evidence retention change. The adapter rereads protection before returning a receipt; denial or unknown responses leave the intent pending. Sufficient protection issues no write, and an accepted-but-lost extension is reconciled on retry without duplicating the version. Purge still waits for independently established logical eligibility **and** provider expiry. This local definition was specifically approved on 2026-10-08; provider behavior and request cost require actual AWS qualification.

There is no approved maximum library byte size yet. Do not promise 24-hour recovery for an unbounded workload or invent a byte envelope. Measure at least 100,000 images and 1,000,000 content/version records, plus actual protected bytes, object-size histogram, monthly growth, snapshot size, copy throughput, full-hash throughput, RDS restore duration, KMS/S3 request volume, quarterly retrieval volume, Fargate hours, NAT use and Glacier Instant Retrieval small-object charges. Obtain a dated ap-southeast-2 estimate and written monthly budget/maximum-byte approval before schedule activation. Stop growth or release qualification when measured bytes exceed that ceiling or the measured restore exceeds 24 hours.
