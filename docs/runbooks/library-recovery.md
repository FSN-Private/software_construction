# Library backup and recovery

**Status:** local software and templates are implemented and under validation. No AWS recovery account has been deployed or qualified. Do not treat a successful local test or an unconfigured workflow as recovery evidence.

## Recovery boundaries

The primary capture task runs in ap-southeast-1 every 15 minutes. It takes a PostgreSQL 18 exported MVCC snapshot, runs `pg_dump` against that same snapshot, and writes a sealed inventory/configuration capture to the primary capture bucket. It uses the independently provisioned, read-only database secret. The recovery account in ap-southeast-2 polls every 5 minutes, assumes the primary read role only while copying, verifies exact source versions and bytes, records recovery-owned write intents, then advances the verified-point watermark only after the joined database and object point is complete.

Protected payload and snapshot copies are versioned, SSE-KMS encrypted, Object Lock governance-retained for at least 90 days, and never expire automatically. Only `payload/` objects move to Glacier Instant Retrieval after 90 days; database dumps under `snapshots/`, manifests, release artifacts, configuration, audit and evidence remain in Standard. The payload bucket's default retention starts when an object version arrives, while logical purge eligibility is measured from the signed proposal and lifecycle state. Those clocks can differ: an exact version can remain locked beyond its logical eligibility time. The purge executor must stop and report that version as pending until S3 permits deletion; never shorten or bypass governance retention. A separate mutable target bucket receives verified bytes under `sha256/{digest}` during isolated restore. The recovered API has permission to that target bucket only; it has no access to the protected payload bucket or primary account. No native S3 replication is enabled because asynchronous replicas can outlive purge writer fencing.

Copy/checkpoint evidence and MFA owner-approval receipts use separate RSA-PSS-SHA256 KMS keys. The recovery worker can sign recovery evidence but cannot sign approvals. Only the separately provisioned MFA owner role can sign the owner-approval key. The API and worker verify approval receipts against an SPKI/fingerprint pin delivered through recovery configuration, never a key embedded in a receipt. The recovery API resolves the new Cognito issuer, audience and subject through the signed server-side binding to the preserved logical owner ID; clients cannot submit an owner ID. A separate, manually invoked ControlTable index-bootstrap task has its own role limited to strongly consistent inventory/index reads and writes; it receives no primary, object-store, evidence, database, signer, or fence access.

## Bootstrap and schedule activation

The independent `verify` task reconstructs an isolated database and reads exact recovery versions with its separate verifier role; it cannot change copy/index records. It persists signed audit/verification and failed-cycle envelopes in the retained verification table. A scoped pending-cycle pointer and envelope are committed atomically; restart drains that original signed message before discovering newer points. Queue retries preserve event IDs and observation timestamps, and never create a healthy point. The role can send only to the configured primary observation queue. The copy and drill roles have no queue send authority. Verification failure/freshness alarms use `WorkerId=verify`; the verifier heartbeat alarm detects a missing 15-minute invocation.

The local template attaches the approved exact runtime-secret read grant and the separately approved support statements from `recovery-verification-reader-support.v1.json`: verifier table-key decrypt only through Sydney DynamoDB with exact table/account contexts, and drill GetItem only on the verification table's POINT/configured OWNER partitions. Keep schedules disabled until actual IAM isolation has been qualified. Local compilation, signed-message fixtures and template checks are insufficient for activation.

Keep `recoverySchedulesEnabled=false` until the independent account, source grants, images, key pins and first complete point have been checked. Use real account IDs and region-specific bucket/key identities for every non-offline command. This repository does not provision or authorize the external reader login, MFA operator role, owner email, alert subscriptions, AWS account, mailbox, VPN or budget approval.

## Monitoring and alert response

The capture, copy and drill tasks emit one-line CloudWatch Embedded Metric Format events to their existing encrypted ECS log group. The metrics use only `Environment` and fixed `WorkerId` dimensions. CloudWatch Logs extracts the metrics from the log events; task roles do not receive `cloudwatch:PutMetricData`.

| Metric/alarm | Limit | Response |
|---|---:|---|
| `VerifiedPointAgeSeconds` | 2,700 seconds (45 minutes) | Treat as unhealthy. Check capture completion, source-reader grants, copy role assumption, pending write intents, destination access, signatures, object retention/access, database/object closure and KMS availability. Do not advance the watermark manually. |
| `RecoveryWorkerHeartbeat` (`WorkerId=copy`) | One successful copy/freshness cycle per 5-minute period | Treat missing data as a breach. Check EventBridge target status, ECS task exit reason, log ingestion and EMF parsing metrics. |
| `RecoveryWorkerHeartbeat` (`WorkerId=capture`) | Three consecutive 5-minute periods without a successful capture | Treat missing data as a breach. Check scheduled capture task, database reader secret, database reachability, scratch storage and dump/upload outcome. |
| `CopyFailures`, `VerificationFailures`, `CaptureFailures` | Any emitted failure | Preserve the signed error observation. Keep the last verified point unchanged; repair and resume by idempotent exact-version receipts. |

The age alarm's 45-minute threshold leaves at most 15 minutes to detect and deliver an alert before the 60-minute RPO boundary. The heartbeat, SNS acceptance and actual email delivery must be measured in a drill; CloudWatch configuration alone does not prove the 15-minute notification objective. A missing point uses the worker's explicit over-threshold sentinel, never a fabricated current timestamp or age of zero. AWS EMF extraction is asynchronous and at-least-once; investigate parsing/validation errors in the `AWS/Logs` namespace and account for duplicate values in failure/heartbeat metrics. See [AWS EMF guidance](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch_Embedded_Metric_Format.html).

## Regional drill

Use the protected GitHub `recovery-drill` environment and the recovery-account OIDC role. The workflow is manual/quarterly and starts only the pre-pinned recovery drill task in isolated subnets, with no public IP, ECS Exec, primary role or deployment credentials. It cannot promote or purge. The current worker restores and validates an isolated database. Payload materialization, temporary private API launch and owner-access checks remain implementation gates; the current task cannot issue a successful qualification. An authorized owner completes the recovery Cognito MFA login separately; the unattended workflow cannot claim that an owner completed an MFA challenge or received a mailbox message. The protected OIDC role can inspect only task/network metadata needed to validate its fixed Fargate task and fetch exact versions of the payload-free qualification and audit-checkpoint artifacts. EC2 describe calls use `Resource: *` because those APIs do not support resource-level scope and are restricted to the recovery region. The role's maximum session is six hours for the measured drill window. A separate manual qualification-export workflow verifies the protected launch record and release bindings, then downloads only those signed safe evidence artifacts; it does not export private manifests, database dumps, or payload inventories.

Before the drill, declare the loss time and measured workload envelope. Capture the primary-denial test before any recovery read, then record the isolated restore start and ready timestamps. A successful qualification must include:

- Both 12-digit account IDs, aliases and regions; source revision; API, ingest-worker, renderer and recovery-worker OCI manifest digests; migration digest; and the recovery template digest.
- A recovery-signed checkpoint, exact manifest digest, snapshot cutoff/LSN/change watermark and expected/observed item counts and byte totals for every required class.
- Actual source-account/region access denial, exact object rehash, database restore, graph/XMP/metadata/audit/configuration/release artifact checks, independent owner authentication and foreign-identity denial.
- Actual recovery notification delivery timestamps, a successful cold retrieval from Glacier Instant Retrieval, retention/final-copy evidence, and the isolated purge fixture including Feature 012 export cleanup acknowledgement.
- Measured `RPO <= 3,600` seconds and `RTO <= 86,400` seconds at or below the separately owner-approved maximum protected-byte workload, no unresolved blocking corrective actions, and exact digest binding to the release under review.

The canonical file is `evidence/drills/<run-id>/recovery-qualification.v1.json`. Its signature covers exact canonical UTF-8 payload bytes; verification must use the independently configured public key and fingerprint. Never trust a public key carried by the qualification file. A failed, incomplete, stale, fixture-only, mismatched or unsigned drill is retained as failure evidence and cannot satisfy release promotion.

## Restore, promotion and purge

For accidental loss, select a fully verified point before the reported change and use a new isolated restore session. Never overwrite the live database or target bucket during validation. Verify that the target point, database graph and exact recovery payload closure agree, and inspect all holds and purge/write-intent fences. A human owner must approve a plan-bound promotion with a fresh recovery MFA identity after validation and generation checks. Keep the previous live generation available for reviewed rollback.

For regional loss, do not use the primary AWS role or a primary-region endpoint. Recreate the recovery app and configuration from the pinned recovery image repositories and database/config snapshots. Authenticate to the recovery Cognito pool over the supported private path, enroll/verify MFA, and create only an independently approved signed issuer/audience/subject-to-preserved-owner binding. Do not overwrite historical graph rows or accept caller-selected owner IDs. Do not automatically reverse-replicate when primary returns; reconcile and cut over through a separate reviewed operation.

Purge means approved media payload deletion only. The approved design retains immutable historical graph rows, hashes, paths, audit records and descriptive metadata in recovery database snapshots; disclose that paths and metadata can remain. Before approval, enumerate active holds, shared content, source and recovery exact versions, pending/unknown write intents, multipart uploads, cold objects and Feature 012 export intents. Require recovery-side fresh hold validation and a signature over the exact scope and plan digest. Do not complete purge until source deletion, recovery deletion, durable export cleanup acknowledgement and provider settlement are independently verified. Routine retirement must preserve the final verified copy. An independently approved, eligible media-only purge may remove its exact final payload copy, but must preserve unrelated protected content and metadata. Never bypass Object Lock governance. Full metadata erasure needs a separately approved graph-redaction design.

The infrastructure defines a separate purge-executor role trusted only from the configured recovery-account MFA operator principal. The user approved this exact local IAM definition on 2026-10-06. It can read owner-point/control and write-intent records; create/update recovery fences; delete fence items only in `SNAPSHOT#*` partitions; list and read exact versions only under `payload/sha256/*` and `snapshots/*`; read `points/*` evidence versions; and delete exact payload/snapshot versions. KMS decrypt is limited to the two recovery storage keys, through regional S3, and to those object-prefix encryption contexts. It has no primary-account, database-secret, owner-approval-key, evidence-signing, evidence-delete, or intent-write access. The application must condition snapshot-fence release on the exact authorized sentinel and signed completion. The approval covers local template code and tests only; it does not authorize deployment, assuming the role, or deleting AWS objects.

## Cost and recovery envelope

There is no approved maximum library byte size yet. Do not promise 24-hour recovery for an unbounded workload or invent a byte envelope. Measure at least 100,000 images and 1,000,000 content/version records, plus actual protected bytes, object-size histogram, monthly growth, snapshot size, copy throughput, full-hash throughput, RDS restore duration, KMS/S3 request volume, quarterly retrieval volume, Fargate hours, NAT use and Glacier Instant Retrieval small-object charges. Obtain a dated ap-southeast-2 estimate and written monthly budget/maximum-byte approval before schedule activation. Stop growth or release qualification when measured bytes exceed that ceiling or the measured restore exceeds 24 hours.
