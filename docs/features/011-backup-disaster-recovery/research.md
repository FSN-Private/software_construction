## Verified AWS capabilities

The proposal relies on official AWS documentation:

| Decision | Evidence and consequence |
|---|---|
| Recovery-controlled payload copies | S3 cross-account replication requires versioning on both buckets and destination permissions. Large objects can take hours, and an out-of-band provider replica is difficult to fence against a later purge. The selected pull/copy worker checks the recovery-owned tombstone and durable writer intents before each write. [S3 replication requirements](https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication-requirements.html) |
| Recovery-owned encryption | Cross-account S3 replication of SSE-KMS data requires a destination customer-managed key and key policy. The selected worker writes recovery objects with the recovery-account key and never gives the primary runtime recovery read/delete rights. [Replicating encrypted objects](https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication-config-for-kms-objects.html) |
| RTC rejected for this path | S3 Replication Time Control reports replication metrics/events and states 99.9% of objects replicate within 15 minutes. This service timing is not the selected copy path because provider-managed writes do not consult purge intents. Its premium and remaining performance limits also do not prove the end-to-end database/object RPO. [S3 Replication Time Control](https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication-time-control.html) |
| RDS backup alternatives | AWS Backup currently supports simultaneous cross-region and cross-account RDS snapshot copies, but cross-account backup requires the accounts to belong to the same AWS Organization. Copies of continuous recovery points become snapshots and do not preserve PITR. The proposal instead shares one PostgreSQL MVCC snapshot between logical dump and exact object inventory and does not add an AWS Backup dependency. [AWS Backup feature availability](https://docs.aws.amazon.com/aws-backup/latest/devguide/backup-feature-availability.html), [cross-account backups](https://docs.aws.amazon.com/aws-backup/latest/devguide/create-cross-account-backup.html), [copying continuous backups](https://docs.aws.amazon.com/aws-backup/latest/devguide/point-in-time-recovery-copying.html) |
| Hourly backup timing | AWS Backup permits hourly snapshot schedules, but uses a job start window, defaults to eight hours, and any configured start window must be at least 60 minutes. Job start, copy completion, and closure verification add delay; hourly cadence alone cannot establish a 60-minute RPO. [AWS Backup plan options](https://docs.aws.amazon.com/aws-backup/latest/devguide/plan-options-and-configuration.html) |
| Aged payload storage | S3 Glacier Instant Retrieval offers online millisecond object access, a 90-day minimum duration, a 128 KB minimum object size, and per-GB retrieval charges. Flexible Retrieval standard restores typically take 3–5 hours; Deep Archive standard restores typically take 9–12 hours. Instant Retrieval is selected for old payloads so retrieval staging does not consume the recovery window; bulk transfer and fees still require measurement. [S3 Glacier classes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/glacier-storage-classes.html), [storage class details](https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage-class-intro.html) |
| Object Lock versus purge | If an S3 source bucket has Object Lock, the destination must also have it. Default lock on every payload version can delay purge and extend a recovery hold from replica arrival. The proposal avoids blanket payload Object Lock and instead uses recovery-owned access controls, copy intents, tombstones, and signed checkpoints. [S3 replication requirements](https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication-requirements.html) |
| Release images | ECR supports cross-region and cross-account image replication; the destination registry must authorize the source. Existing deployed digests must be seeded, retained, and checked before recovery is healthy. [ECR image replication](https://docs.aws.amazon.com/AmazonECR/latest/userguide/registry-settings-configure.html) |
| Owner identity | Cognito documents multi-region replication with KMS, feature-plan, and operation limitations. It does not itself establish an independently administered recovery-account identity. The proposal rebuilds the pool in recovery and needs the verified owner mailbox for first login/password reset, plus independent recovery-account MFA custody. [Cognito multi-region replication](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-multi-region.html) |

## Alternatives and feasibility

- A second region in the current account does not meet the separate recovery-account boundary.
- Native S3 CRR/RTC can provide efficient replication and useful lag signals, but leaves destination writes outside recovery purge/writer-intent control. Explicit recovery-side copying costs transfer, hash, and worker capacity; its measured closure time must stay below the verified-point age limit.
- AWS Backup/RDS hourly snapshots remain a possible future alternative, but their schedule and copy jobs do not establish the joined PG/S3 point and the cross-account setup imposes an AWS Organizations relationship. The selected native PostgreSQL dump uses one exported MVCC snapshot for the database and exact dependency inventory; capture duration and database load must be measured.
- Flexible Retrieval and Deep Archive have lower storage cost but slower retrieval. Glacier Instant Retrieval has higher access charges and a small-object billing floor. It is the proposed tradeoff for old payloads while database/catalog/config/release/owner evidence remain warm.
- Payload-only purge preserves historical graph/audit metadata while deleting eligible original/XMP bytes and preventing normal restore from returning them. Full erasure of hashes, paths, commit manifests, and older database captures would need a separate graph-redaction design and owner decision.

The 15-minute dump/copy interval is only a candidate. RPO evidence must compare declared loss time to the cutoff of the newest fully verified recovery point, prove all acknowledged mutations through that cutoff via the transactional ledger, and prove the exact payload closure exists. RTO must restore the complete approved byte envelope and owner access, not only a representative fixture. At present, no defensible dollar estimate or 24-hour guarantee exists because total bytes, size distribution, growth, and throughput are unknown.

## Implementation constraint checks, 2026-10-05

The approved safe-summary mirror must stay independent of inventory size. The primary queue carries signed point metadata, full-manifest/checkpoint digests and class totals; exact object locators and full closure manifests remain in recovery-owned storage. SQS currently limits an individual message to 1 MiB, and the importer deliberately applies a smaller bound. [AWS SQS message quotas](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/quotas-messages.html).

Durable DynamoDB records must likewise remain bounded metadata or exact-version pointers to signed S3 artifacts, rather than one embedded full-library closure. DynamoDB limits an item to 400 KiB including attribute names and values. Per-object write intents remain individually bounded. [AWS DynamoDB constraints](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Constraints.html).

## Worker dependency assessment (2026-10-05)

The recovery worker adds exact-version AWS SDK packages for DynamoDB durable catalog/write intents, KMS RSA-PSS signing, Secrets Manager database credentials, STS scoped source reads/account identity, and SQS safe result publication. Existing S3 and Npgsql dependencies are reused through project references. `apps/recovery-worker/packages.lock.json` records resolved versions and content hashes; the new services require AWS SDK Core 4.0.102.8 in the worker dependency graph. No new package feed or package installation script is introduced. The official [DynamoDB package](https://www.nuget.org/packages/AWSSDK.DynamoDBv2/4.0.107) and [STS package](https://www.nuget.org/packages/AWSSDK.SecurityToken/4.0.101.1) identify `awsdotnet` ownership and Apache-2.0 licensing. The live NuGet advisory check including transitive worker dependencies reported no known vulnerabilities; see [validation.md](validation.md). Recheck advisories and locked restore when these pins change, and remove any service package unused by the completed commands (NFR-004, NFR-009, NFR-015).
