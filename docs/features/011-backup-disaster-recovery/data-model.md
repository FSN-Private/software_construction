# Backup and Recovery Data Model (proposal)

**Status:** Approved for local implementation on 2026-10-05.
**Feature:** [011 Backup and Disaster Recovery](spec.md)

This model adds recovery evidence around the existing PostgreSQL and S3 authorities. It does not change the identity of an asset, edit, XMP object, or commit. The primary database remains the source of live state; the recovery account owns independent copies, verification receipts, restore isolation, purge receipts, and signed audit checkpoints.

## Existing authorities

| Data | Current authority | Recovery requirement |
|---|---|---|
| Original and XMP bytes | Immutable `sha256/{digest}` objects. `content_objects` records digest, byte length, category, key, exact S3 version, and integrity state. | Copy each referenced exact source version. Recompute SHA-256 and byte length from bytes read back in the recovery region; provider metadata alone is insufficient verification. |
| Asset, edit, path, lifecycle, provenance, and holds | PostgreSQL tables created by migrations 005 and later. | Capture one transactionally consistent full database recovery point, including schema/migration identity. |
| Version graph | Immutable `vc_commits.manifest_bytes`, normalized parent/entry rows, plus mutable refs, reflogs, visibility, working/staging state, and recovery expirations. | Preserve the manifest bytes and every required graph row in the same database point. Rebuild only derived projections after graph and exact XMP-content validation. |
| Purge/export state | Feature 012 tombstones and durable write intents, with completion acknowledged by `ExportInvalidationService`. | Include pending invalidations and cleanup evidence. A backup containing a purged object is denied to normal restore workflows by the independent purge journal. |
| Audit | `audit_events` and selected append-only VC evidence. | Export relevant recovery events to the independently controlled audit ledger and verify continuity before promotion. |
| Previews and other regenerable derivatives | Separate derivative bucket and materialized indexes/projections. | Classified as disposable unless a later approved requirement changes this classification. Rebuild after restore. |

The existing reconstruction manifest (`packages/storage/Reconstruction/ManifestService.cs`) is a useful seed inventory but is not a full recovery point: it exports selected ingest tables and does not snapshot the complete `vc_*`, export, rendering, configuration, and recovery state. A 011 recovery point must bind a complete database snapshot to a versioned object inventory, rather than treating a current reconstruction manifest as a database backup. A `pg_dump` also omits AWS/IAM/Cognito configuration, release image artifacts, and secret values; versioned non-secret access/configuration evidence and immutable release identities are captured separately, while credentials are re-established from independent recovery identities and keys.

## Proposed records

Names below are logical schema names; the migration may use the repository's `recovery_*` naming convention. Records that prove completed work are append-only. Mutable status is isolated to explicit state or acknowledgement columns.

| Record | Required fields and constraints |
|---|---|
| `recovery_points` | `id`, `owner_id`, `library_id`, `schema_version`, `source_region`, `captured_at`, `database_snapshot_ref`, `database_snapshot_digest`, `inventory_ref`, `inventory_digest`, `change_watermark`, `state`, `verified_at`, `verification_codes`, `retention_until`, `archive_state`, `created_at`. A point becomes `verified` only after the database snapshot is readable and its complete inventory has passed byte and relationship checks. Keep point identity immutable; append verification attempts rather than replacing a prior result. |
| `recovery_point_components` | `recovery_point_id`, component kind and immutable source identity/version, recovery identity/version, digest, byte length, and verification result for schema/migration state, non-secret runtime configuration, release artifacts, owner/access-policy configuration, database dump, object inventory, and recovery journal. Never copy credentials or secret values. |
| `recovery_point_items` | `recovery_point_id`, `data_class`, logical scope (`asset_id`, optional `edit_id`, optional `commit_id`), content SHA-256, byte length, source key/version, recovery key/version, source lifecycle generation, and item verification result. Unique per recovery point and logical scope plus digest/version. Keep object locators inaccessible to owner-facing responses. |
| `recovery_write_intents` | `id`, recovery point/session, lifecycle generation, exact source and unique destination scope, data class, writer identity, state (`admitted`, `storage_pending`, `unknown`, `settled`, `cleaned`), multipart/provider receipt, and settlement evidence. Every replica, archive transition, database snapshot, and retry must have an intent or equivalent provider proof. A purge closes admission and cannot finish while an earlier admitted writer may still publish. |
| `recovery_verifications` | `id`, `recovery_point_id`, start/completion time, verifier build, covered classes/counts, recomputed byte results, graph/database results, exception codes, and alert receipt. Append-only; failures remain visible after a later successful retry. |
| `recovery_restore_sessions` | `id`, owner/library, recovery-point ID, scope, requested logical IDs, request operation/idempotency fingerprint, requesting actor and `auth_time`, isolated target ID, state, created/updated/deadline, validation digest, failure codes, and promotion ID. States: `requested`, `restoring`, `validating`, `ready`, `promoting`, `promoted`, `aborted`, `failed`, `expired`. The target has a unique session namespace and cannot be read by ordinary asset, lineage, render, or export queries. |
| `recovery_validation_results` | `session_id`, validation schema/version, target snapshot identity, exact object-byte results, asset/edit associations, XMP and commit-graph findings, metadata/access-policy findings, purge exclusions, audit checkpoint, validation digest, and completion time. Append-only. Any error leaves the session non-promotable. |
| `recovery_promotions` | `id`, session, scope, expected live lifecycle/environment generation, target generation, actor, fresh-auth time, explicit confirmation digest, operation/idempotency key, state, result, and audit event. Promotion is a compare-and-swap against the expected live generation and is idempotent. |
| `recovery_retention_holds` | `id`, recovery point/item scope, reason, source reference, created time, expiry, and release evidence. Active 90-day deletion/rewrite obligations and pending recovery/purge workflows hold the exact relevant recovery items. |
| `recovery_owner_bindings` | Verified recovery `issuer`, `audience`, and new authentication `subject` mapped to the preserved canonical database `owner_id`, with independent approval actor/MFA receipt, created time, and revocation evidence. Bindings are server-side, append-only/versioned, and never accept an owner ID from a client request. |
| `recovery_purge_operations` | Immutable operation ID and logical scope; category/digest and exact primary/recovery payload versions plus derived/export media destinations; proposal actor/time/evidence; independently approved actor, MFA context/time, exact plan digest and signature/receipt; lifecycle generation; independently recomputed eligibility; export tombstone event; current phase and timestamps; primary deletion receipt; recovery deletion receipt; final version-enumeration receipt; completion audit ID. Keep state transitions in append-only `recovery_purge_steps`, not by rewriting the original request. |
| `recovery_audit_events` | Independent monotonically increasing sequence, event UUID, schema, owner/library, operation ID, event type/outcome, safe logical resource ID, timestamp, previous hash, canonical event hash, signer key ID/signature, and remote receipt. Verification starts from a recovery-account-signed immutable genesis/checkpoint and an owner-held public-key fingerprint/checkpoint stored out of band; a self-computed unanchored hash chain is not tamper evidence. Never store image bytes, XMP payload, secret credentials, or private paths. Corrections append a new event. |

Every object item binds both the logical identity and exact physical version. Content-addressed deduplication does not merge logical asset/edit lifecycles: purge and restore authorization always include owner/library and asset/edit scope. A physical version is deleted only when no non-purged eligible identity still references it.

## Recovery point contents

A recovery point is a matching pair of a consistent full database snapshot and a canonical, checksummed object inventory. The inventory includes all authoritative originals and XMP objects referenced by live or recoverable assets, commit base/current content, publication provenance, and required recovery metadata. The database snapshot preserves all operational tables needed to reconstruct current private access and history, including migration version, asset/edit/path/lifecycle state, holds, publication and upload provenance, audit, commit manifests/parents/entries, refs/reflogs/visibility, working/staging/checkouts/stashes, purge tombstones, export invalidation/cleanup state, and recovery records. Derived gallery, lineage reachability, preview, and cache rows are classified as rebuildable and must not be mistaken for authoritative history.

The proposed capture cadence is a coordinated full PostgreSQL `pg_dump` from one exported transaction snapshot every 15 minutes, paired with object-version inventory and recovery-side writes. The capture records a source watermark and a point-in-time database identity before publishing the recovery point. No point is called complete while a required object copy or corresponding database snapshot is pending. A database point whose object references fall outside the copied inventory is incomplete. The conservative one-hour RPO measurement uses declared-loss time minus the newest fully verified snapshot cutoff, and proves that all acknowledged changes through that cutoff are represented by the transactional watermark. The time of an idle library's last mutation is not its recovery-point age. Each 15-minute capture must finish, copy, and verify within the remaining RPO budget; the schedule alone does not prove the objective.

Cold copies retain the same inventory identity and remain subject to the independent purge journal. Any long-term retention mechanism must allow a policy-eligible media purge to complete after all 90-day holds expire; legal or provider-level immutability beyond that date would contradict FR-017 and must be explicitly approved.

Under the recommended media-only policy, the coordinated `pg_dump` contains database rows and immutable graph manifests but no original or XMP media payload bytes. Those snapshots therefore do not need row-level rewrite or wholesale retirement to complete media purge; their asset/edit/path/graph metadata may remain and must be fenced by the independent purge tombstone before any restored environment opens normal access. The exact photo/XMP bytes and every media-bearing copy remain subject to physical deletion and version enumeration. If an implementation later embeds media payload in a database snapshot, it must either prove that every such snapshot/version is removed or pause purge completion pending a separately approved sanitization design.

## State invariants

- Only a verified recovery point can start a restore. A failed or partial copy is not a recovery point.
- Restore writes into a session-owned isolated database/schema or environment and a session-owned object namespace. It never changes live asset rows, refs, object versions, DNS, or active environment selection.
- Validation reads the recovered bytes and recomputes SHA-256 and length. It checks exact source-version identity, asset/edit associations, manifest digest/canonical form, commit parents and entries, XMP availability, metadata consistency, private owner/access policy, audit continuity, and all applicable purge tombstones.
- Promotion requires a successful immutable validation result, a fresh owner authentication, explicit confirmation bound to the validation digest and expected live generation, and a durable audit receipt. A collision or changed generation returns a conflict and leaves the isolated session intact.
- Reconstructed access uses a recovery-only server-side mapping from a cryptographically verified `(issuer, audience, new subject)` to the original canonical `owner_id`. Create or change this binding only with independent recovery-account owner MFA and an immutable audit receipt. Never rewrite existing database owner IDs or accept a caller-supplied canonical owner ID; foreign subject, issuer, audience, or owner group fails closed.
- Permanent purge requires an independent recovery-account owner authentication with MFA and explicit approval over the exact logical scope, digest/version set, lifecycle generation, and plan digest. Primary API requests and claims from the primary database are proposals only; the recovery executor independently recomputes eligibility and active holds from trusted recovery evidence before authorizing deletion.
- Automated retention cannot expire the last independently verified recoverable copy for any still-protected logical object or class. An authorized permanent purge is the explicit exception for its expired logical scope; it cannot discard the last valid copy of unrelated, still-protected data.
- Backup, replication, snapshot, and archive writers are admitted through durable unique-destination intents. Purge closes new admission under the same logical lifecycle fence, waits for provider operations to settle, deletes exact completed versions, and reconciles pending/unknown writes before acknowledging completion. A late replica after acknowledgement is a correctness failure.
- Purge completion requires durable tombstones in both failure domains, expiration of all applicable holds, acknowledged feature 012 cleanup, deletion of all eligible exact versions in primary and recovery storage (including noncurrent versions and archive copies), and a final enumeration receipt. Unknown outcomes stay pending and deny access; a timeout is never evidence of deletion.
- A purge tombstone and its safe completion proof survive deletion of the protected payload. A backup restored later applies the tombstone before any normal access is opened.

## Current implementation seams

- Add the independent object adapter under `packages/recovery/RecoveryObjectStore.cs` with a recovery-account destination and exact-version streamed read/write verification. `S3ObjectStore.VerifyStoredAsync` validates S3 metadata; `S3Transfers.ReadVerifiedAsync` already hashes actual returned bytes and is a suitable primitive to reuse or factor.
- Add schema through an additive migration after `021_export_baskets.sql`; do not rewrite old migration bytes.
- Keep shared versioned types in `packages/recovery/RecoveryContracts.cs`, live health/session operations in `apps/api/Features/Recovery/`, and long-running/outage operations in `apps/recovery-worker/`; register the API services from `apps/api/Program.cs`. The worker's executable, credentials, configuration, and runbook must have an independent bootstrap path.
- Keep purge publication inside the trusted in-process boundary used by `ExportInvalidationService`; do not expose a generic endpoint that lets a caller synthesize a feature 012 tombstone.
- Add an opt-in independent recovery stack under `packages/infrastructure/src/recovery/`, wired from `packages/infrastructure/src/app.ts`, only after recovery-account trust, region, key ownership, cold-tier policy, workload and purge behavior are approved. Current primary stack is single-account and configures seven days of RDS backup retention.

## Recommended purge scope for approval

For current v1, recommend physical erasure of the exact original and XMP media payloads and all service-controlled payload copies, including recovery/archive versions, rendered image derivatives, export packages, temporary workspaces/staging/quarantine copies, and multipart remnants. Keep immutable graph, asset/edit identity, hashes, path history, descriptive metadata, audit evidence, and purge tombstones. Tombstones must deny ordinary download, render, export, and restore access to the purged logical scope, including when an older database snapshot is restored. This intentionally means a private path or descriptive metadata may remain in historical database snapshots after the media is gone; owner approval of that remaining metadata is required.

PostgreSQL `vc_commits.manifest_bytes` contains canonical graph JSON (hashes, paths/lifecycle and commit evidence), not raw XMP bytes, and migration 006 rejects commit/entry updates or deletion. The recommended scope preserves those immutable bytes to keep existing commit IDs and graph integrity valid. Full private-metadata erasure is a separate owner alternative requiring a designed redacted-graph representation, new integrity rules, and recovery-snapshot sanitization. Do not silently treat sensitive path/descriptive metadata as purged, and do not silently rewrite immutable graph history. Service purge cannot erase copies already downloaded to devices or other owner-controlled systems outside the service boundary.
