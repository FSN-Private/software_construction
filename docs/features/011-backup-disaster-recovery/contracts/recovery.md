# Recovery, retention, and purge contract v1 (proposal)

**Status:** Approved for local implementation on 2026-10-05.
**Feature:** [011 Backup and Disaster Recovery](../spec.md)
**Data model:** [data-model.md](../data-model.md)

Feature 011 owns backup classification, verified recovery points, isolated recovery, promotion authorization, recovery retention, and permanent purge of originals/XMP plus required recovery copies. Feature 012 consumes Feature 011's trusted purge handoff; it does not authorize or synthesize purge events.

## Authority and credentials

The recovery account and region are a separate security boundary. The primary runtime publishes capture artifacts only into its own account. The recovery worker pulls those artifacts using narrowly scoped primary read access during normal backup operation; it alone writes recovery copies using recovery-account credentials. The primary runtime cannot read, delete, change retention on, or administer the recovery copy, its KMS key, its audit ledger, or its recovery identities. The recovery operator role is authenticated independently of the primary AWS account and primary-region identity runtime. Its credentials and MFA recovery method are held outside the primary account and region. A concrete bootstrap proposal is a dedicated recovery-account IAM Identity Center identity protected by MFA, with owner-held recovery credentials and a recovery-only role; no primary Cognito or primary AWS identity is trusted for outage authorization. Recovery restore/purge operators must not be able to use the producer identity as a substitute for independent owner authorization.

Recovery reads and restore commands use recovery-account credentials directly. An outage procedure must not fetch a secret from the primary account, invoke the primary API, use primary Cognito, or require primary-region service availability. A normal in-app health view is useful only while the primary service is available; the same recovery health report and runbook must be available from the independent recovery control path.

The selected capture proposal is a coordinated full PostgreSQL `pg_dump` from one exported transaction snapshot every 15 minutes, with a matching authoritative-object inventory and exact object-version recovery copy. The database dump is a logical recovery artifact rather than a same-organization AWS Backup/RDS snapshot dependency. The proposed destination is independently administered `ap-southeast-2` storage, with independent KMS custody and approved cold tiering. Recovery-controlled copies replace the parent research's S3 RTC/CRR suggestion so writes have explicit admission and settlement evidence during purge. Account bootstrap, trust principals, region, KMS key custody, archive class, and alert destination must be configured before claiming FR-002/003/016 or the binding RPO/RTO gates.

## Recovery point and health behavior

The backup producer captures a transactionally consistent full database point and a canonical inventory bound to exact object identities. A point is `verified` only after all protected classes are present, required exact versions can be read from the recovery failure domain, actual byte streams recompute to the recorded SHA-256 and length, and database/graph relationships validate. A declared hash, an S3 metadata checksum, replication status, or a successful job exit alone is not verification.

The point records its snapshot cutoff and a transactional acknowledged-change watermark represented by both its database snapshot and all referenced object versions. The conservative recovery-point age is declared-loss time minus the newest verified cutoff, with proof that every acknowledged mutation through that cutoff is represented. An idle library does not become stale merely because its most recent mutation is old. A point is incomplete if any protected class, referenced byte version, graph record, metadata row, purge journal entry, or audit checkpoint is missing. The recovery catalog never reports a partial point as healthy. Failure, lateness, incomplete coverage, byte mismatch, inaccessible KMS key, and alert-delivery failure are separate safe status codes.

An overdue, incomplete, inaccessible, or integrity-failed required class emits owner/operator notification within 15 minutes. Health output uses localized text labels and unambiguous UTC timestamps/digests; it does not reveal object locators, private paths, secrets, media content, or another owner's records.

## Proposed HTTP contract

All endpoints are owner-scoped and require the existing authenticated owner policy while the primary runtime is available. Mutations require `Idempotency-Key`, operation ID, and the relevant lifecycle/environment precondition. Restore creation and promotion require authentication no older than five minutes, as checked from verified `auth_time`; a client header cannot substitute for recent authentication. This primary authentication is sufficient to prepare an isolated restore but never authorizes recovery-account deletion. Responses use opaque IDs and safe problem codes and never expose storage locators or recovery credentials.

| Method and path | Request and result |
|---|---|
| `GET /v1/recovery/health` | Owner-readable current status by protected class: latest point age, coverage, byte/graph integrity, last successful verification, pending exceptions, and last alert status. `200` may carry `degraded`; return `503` only when the status source itself is unavailable, with a safe code. |
| `GET /v1/recovery/points?limit={n}` | Lists owner/library recovery-point IDs, captured/verified times, covered classes, retention state, and safe integrity status. Never exposes source or destination keys. A failed point remains visible as evidence but cannot be selected for restore. |
| `POST /v1/recovery/sessions` | Body: `{ "recoveryPointId": "…", "scope": { "kind": "library" | "asset" | "edit", "assetId": "…", "editId": "…" }, "reason": "…" }`. Returns `202` and an opaque session ID in `requested` state. A library restore and an object restore both start in an isolated target. Duplicate idempotency key returns the original session; changed payload with the same key is rejected. |
| `GET /v1/recovery/sessions/{sessionId}` | Returns state, captured point ID, completion/expiry times, progress phase, validation digest when available, and safe exception codes. It does not grant access to restored bytes before validation and promotion. |
| `POST /v1/recovery/sessions/{sessionId}/promotion` | Body: `{ "validationDigest": "…", "expectedLiveGeneration": 7, "confirm": true }`; also requires matching `If-Match` and `Idempotency-Key`. Promotes only a session in `ready` state whose current immutable validation digest matches, whose owner and access policy validate, whose purge exclusions are applied, and whose expected live generation still matches. Success appends a recovery event and returns promotion ID/new generation. |
| `POST /v1/libraries/{library}/purges/prepare` | Body identifies exactly one asset or edit, expected lifecycle version, and reason. Returns an opaque plan, affected logical scope, eligible time, active holds, remaining export/recovery acknowledgements, copy counts by failure domain, and a digest bound to the plan. It does not create a tombstone or delete data. |
| `POST /v1/libraries/{library}/purges/{operationId}/confirm` | Body: `{ "planDigest": "…", "confirm": true }`; requires recent primary owner authentication, `If-Match`, and `Idempotency-Key`. Rechecks the plan under the shared lifecycle lock and creates a proposal only. Returns `202` with phase `awaiting_independent_approval`; it cannot force past an active hold, unexpired 90-day obligation, final-copy guard, pending writer, or unavailable recovery account. |
| `GET /v1/libraries/{library}/purges/{operationId}` | Returns phase, eligibility, pending export/recovery acknowledgements, and completion evidence ID. A `completed` result means exact eligible copies were deleted and independently enumerated absent; `pending` or `failed` never means bytes are gone. |

The HTTP API is not the disaster-recovery control path. An independent recovery command/operator interface must expose `health`, `list-points`, `restore-isolated`, `validate`, `promote`, `drill`, `approve-purge`, and `purge-status/reconcile` using recovery-account credentials. For a purge, the primary API supplies only a proposal. The owner signs into the recovery account with its separate MFA identity and reviews/signs the exact owner/library, asset/edit, category, digest/version set, lifecycle generation, eligibility evidence, and plan digest. The recovery-side executor independently checks the latest trusted recovery point, active holds, recovery-copy inventory, export acknowledgement, pending writers, and purge history before it accepts that signature. It rejects any mismatch or stale/foreign proposal. A forged primary database row, primary application claim, or primary producer credential alone cannot produce a recovery deletion authorization. A regional restore must remain executable with the primary API and database unavailable. The implementation may reuse domain services, but its executable, credentials, configuration, and runbook must have an independent bootstrap path.

Stable safe errors include `recovery_unavailable`, `recovery_point_not_found`, `recovery_point_unverified`, `restore_validation_failed`, `restore_not_ready`, `restore_expired`, `owner_scope_mismatch`, `authorization_boundary_failed`, `stale_live_generation`, `promotion_confirmation_required`, `recovery_audit_unavailable`, `purge_not_eligible`, `retention_hold`, `final_recovery_copy`, `export_cleanup_pending`, `recovery_copy_pending`, `purge_plan_stale`, and `purge_outcome_unknown`.

## Restore isolation and promotion

Restore work is asynchronous. It reconstructs a full isolated database/environment for regional drills and loss, or a session-owned isolated object/metadata namespace for accidental deletion. All writes use unique session destinations and immutable write intents. Normal library asset, lineage, render, download, and export queries cannot address those destinations.

Validation reads recovered object bytes and recomputes each digest/length. It verifies original identity; XMP/edit identity and association; canonical version-control manifests, parents, entries, and graph reachability; library metadata and owner policy; audit-chain continuity; configuration version; and purge tombstones. It reports all safe finding codes and cannot be overridden by a client-supplied `healthy` flag. Any mismatch blocks promotion.

Object-level promotion runs under the owner/library lifecycle lock. It compares the expected live generation and lifecycle version, then integrates the recovered object as a new or restored logical identity according to the validated scope. It does not silently replace a newer live original, XMP state, path, branch, or commit; a collision returns `stale_live_generation` or a specific conflict and leaves the isolated copy available for review. The original recovered data remains attributable to its source recovery point and restore session.

Full-library disaster promotion operates on the isolated recovered environment. The runbook records the declared outage, decision owner, selected verified point, achieved RPO/RTO, validation receipt, independent owner access, traffic/cutover action, abort threshold, and rollback limit. It never restores over the damaged primary environment. If the primary region returns, reconciliation is a separate reviewed action; there is no automatic reverse replication that could overwrite recovered changes.

## Reconstructed owner identity

The current owner ID is derived from the verified primary Cognito subject and is persisted in asset, audit, graph, and export rows. A recovery region may provision a new identity pool whose subject differs. Before access is enabled, an independently MFA-authenticated owner creates an audited server-side binding from the new verified `(issuer, audience, subject)` to the preserved canonical database `owner_id`. The authorization layer derives the binding only from the validated token claims plus required owner group; it never accepts `owner_id` from the URL, request body, or client storage. Do not rewrite historical owner IDs in restored database rows. A foreign subject/group, unverified issuer/audience, missing/revoked binding, or mismatched library fails closed. The recovery binding and its approval receipt are retained in the independent recovery control plane so the primary Cognito pool is not needed.

## Retention and final purge

Soft deletion and displaced-commit retention keep the current 90-day behavior. Existing asset deletion is a recoverable lifecycle change in `AssetService`; rewrite/deletion reflogs and `HistoryRetention` keep displaced commit content through expiry. These holds must feed the recovery retention decision. A storage lifecycle rule must not expire authoritative `sha256/*` bytes or recovery copies based only on age.

Automatic expiration is fail-closed. It first computes whether every remaining protected logical object/class retains a separate independently verified recovery copy covering the required retention horizon. A purge for one authorized, expired logical scope is allowed to remove its final copies only for that scope after all recovery, legal/product, history, export, and audit obligations expire; it cannot remove the last recoverable copy for unrelated protected objects or classes.

Permanent purge uses a durable state machine:

1. Under the common lifecycle lock, revalidate the owner authorization, expected lifecycle generation, 90-day deadline, graph/ref holds, recovery-point holds, deduplicated references, export state, and independent-account availability.
2. In the same transaction, append the immutable purge tombstone and recovery purge operation, reserve the next lifecycle generation, and close new reads/restore/promotion/export and backup-copy admission for only the authorized logical scope. Create durable intents for every already admitted write. Tombstone publication to the independent account must be acknowledged before any payload deletion or snapshot rewrite.
3. Invoke Feature 012's trusted `ExportInvalidationService` with the exact event ID, owner/library/asset/edit/category/digest/generation/evidence. Wait for its durable cleanup acknowledgement, proven writer quiescence, and deletion of all affected package versions/multipart remnants. Never infer an event from an S3 404.
4. Wait until every admitted backup, replication, snapshot, archive-transition, export, and restore writer has verifiable quiescence. A lease timeout or local worker shutdown alone is insufficient. Reconcile unknown copy outcomes by provider receipts and destination inventory; reject new writes using the closed generation.
5. Delete the eligible exact primary and recovery object versions, including noncurrent and archived versions. Preserve bytes still referenced by another active/recoverable logical identity, and scope tombstones so those other identities remain valid.
6. Under the recommended media-only policy, database dumps and `vc_commits.manifest_bytes` contain metadata/graph references, not original or XMP payload bytes, so they remain intact to preserve historical commit identity and integrity. Independently enumerate all primary/recovery media-bearing stores and versions, including archive, derivatives, exports, staging/quarantine, temporary workspaces, multipart remnants, and any known snapshot that actually embeds media bytes. If any media-bearing database snapshot or unknown copy cannot be enumerated and removed, keep the purge pending.
7. Persist primary and recovery enumeration receipts and append the completion event to the independent audit ledger. Only then expose `completed`; older database snapshots remain restoreable only after the independent purge journal has been applied and the purged logical scope is blocked from normal reads/restores.

Every phase is idempotent and restartable. If a delete call has an unknown outcome, an account or archive is inaccessible, an export writer has not proven quiescence, the independent journal has not acknowledged a tombstone, or version enumeration fails, leave the operation pending, keep normal admission closed for the purged scope, retry and alert. A stale recovery point is not a bypass: all restore operations apply the latest independently acknowledged tombstones before opening access.

The export publisher/consumer must preserve the lock order and fencing rules in [Feature 012's purge invalidation contract](../../012-versioned-export-basket/contracts/purge-invalidation.md). In particular, admitted package writes remain tracked until storage is quiescent; lease expiry or a lost callback is not deletion proof. Apply the same admission/settlement invariant to backup and replication writers so a delayed copy cannot recreate purged bytes after acknowledgement. Keep tombstones and non-sensitive purge evidence after payload removal.

## Purge scope requiring approval

**Recommended current-v1 policy for owner approval:** permanently erase the exact original and XMP media payloads and every service-controlled payload copy, including primary, recovery, cold archive, media-bearing temporary/staging/quarantine copies, rendered image derivatives, export packages, and multipart remnants. Retain asset/edit identity, non-reversible content digests, immutable commit/graph evidence, path history, descriptive metadata, audit proof, and the purge marker. The independent tombstone denies all normal content access to that logical scope, including from old recovery points. Other logical identities that share deduplicated bytes retain access only if their own lifecycle remains eligible. This policy does not erase sensitive paths/descriptive metadata from historical DB snapshots; that limitation must be shown in owner-facing purge confirmation.

Full private-metadata erasure is a separate owner alternative. `vc_commits.manifest_bytes` contains hashes plus path/lifecycle fields and normalized commit entries have immutable triggers. Removing eligible metadata from those records requires an owner-approved redacted-graph representation and validation rule; it cannot silently rewrite old commit identity or bypass the existing immutability contract. `pg_dump` snapshots contain these database rows but no original/XMP payloads, so the recommended media-only policy retains them. T006 must record the selected policy and owner acknowledgement of retained metadata before T019/T020 implement irreversible erasure. Purge covers service-controlled copies; it cannot remotely erase copies already downloaded to owner-controlled devices or systems.

## Tamper-evident audit

`audit_events` remains the application transaction log but is not by itself a tamper-evident recovery ledger. Recovery events are appended to an independent, ordered hash chain. Canonical event bytes include event ID, owner/library, operation, safe logical resource, event type/outcome, timestamp, prior event hash, and schema version. The independent writer assigns sequence and previous hash, cryptographically signs each event or periodic checkpoint with a recovery-account-controlled private key, and returns an immutable receipt. The recovery account stores a signed immutable genesis/checkpoint in a dedicated protected prefix; the owner also keeps its key fingerprint and trusted checkpoint outside both AWS accounts as an offline pin. Verification first retrieves and verifies that recovery-owned anchor against the offline pin; missing, altered, or untrusted anchor fails closed. A hash chain whose only root is stored beside itself is insufficient. The primary database stores the receipt/outbox status but cannot rewrite the independent event, anchor, or signer key.

Promotion, independent purge approval, and purge completion require an acknowledged independent receipt. Backup creation records an outbox event transactionally and reports the point as pending until the event/checkpoint is durable. If the audit sink or trusted anchor is unavailable, recovery changes fail closed; this does not suppress an alert for the failure. The quarterly drill verifies the chain from the independently pinned checkpoint and records achieved RPO/RTO and corrective actions.

## Required verification

The feature test plan should map the following to numbered tasks and acceptance criteria:

- Migration rehearsal proves additive rollout, rollback of an uncommitted migration, immutable recovery-point/tombstone/audit rows, and compatibility with existing asset, version-control, and export tables.
- Backup integration captures concurrent acknowledged asset/XMP/commit changes and proves one consistent database point plus exact source-version inventory. Inject omitted classes, missing versions, bad manifest digest, incomplete replication, failed archive retrieval, corrupt bytes with correct declared metadata, duplicate jobs, and lost completion receipts; none may produce `verified` health.
- Recovery storage tests download exact destination versions and recompute content hashes from bytes; test missing, altered, truncated, extra, mis-associated, and wrong-version objects. Do not accept only S3 `HEAD` metadata as byte verification.
- Full restore tests restore a complete database and representative originals/XMP to an isolated environment, verify manifests and graph integrity, owner/access-policy checks, audit continuity, and purge exclusions, and prove normal endpoints cannot see the isolated state.
- Recovery identity tests prove the independently approved new `(issuer, audience, subject)` binding can access only rows for the preserved canonical owner; foreign subject, missing owner group, changed issuer/audience, revoked binding, and client-supplied owner IDs are denied. Existing restored database owner IDs remain byte-for-byte unchanged.
- Promotion tests require recent authenticated owner identity, matching validation digest, exact expected generation, idempotent replay, and explicit confirmation. Race newer live changes, path conflicts, concurrent purge, and stale promotion; no scenario may silently overwrite current state.
- Retention tests prove that expiring one point is rejected when it would remove the last verified copy of still-protected data, while an eligible scoped purge may complete without deleting deduplicated bytes still held by another identity.
- Purge authorization tests prove a primary API/DB forged row cannot authorize deletion; the recovery-side executor requires an independently MFA-authenticated owner signature bound to the exact plan/scope digest and independently rechecks retention/holds against trusted recovery evidence. Stale, replayed, foreign-scope, altered, or unauthenticated approvals fail closed.
- Purge fault tests pause export and backup/replication uploads around tombstone publication, lose callbacks/workers, and inject cross-account delete/version-list failures. The tombstone must fence reads and new writers, keep completion pending until all admitted writers are quiescent and full version enumeration finishes, deny restoration from stale points, and retain signed audit evidence.
- Audit tests verify signatures against the recovery-account immutable genesis/checkpoint plus the owner's offline public-key pin, and fail closed when the anchor is missing, changed, untrusted, or unavailable.
- Infrastructure tests inspect the synthesized recovery account/bucket/key policies: primary roles have no recovery read/delete/admin/approval authority; recovery operators do not require primary credentials; destinations are private, encrypted, versioned, protected against primary-side deletion, and permit an eligible purge after required holds expire.
- A scheduled quarterly isolated disaster drill records the last acknowledged change, selected recovery point, measured recovery-point age, core access restoration time, independent owner authentication, alert outcome, audit checkpoint, and corrective actions. Demonstrate RPO <= 1 hour and RTO <= 24 hours; a model-only or mock restore is not sufficient evidence.
- Owner-facing contract tests verify localized accessible health text, class coverage/freshness/integrity/exceptions, no storage locator leakage, safe status errors, and alert delivery within 15 minutes of detecting a required-backup failure.

Exact task locations: pure contract/hash/retention checks in `tests/recovery/Program.cs`; additive migration, identity binding, and real PostgreSQL/object-storage integration in `tests/integration/recovery/run.mjs`; actual Feature 012 publisher/download/cleanup coverage in `tests/integration/exports/run.mjs`; synthesized recovery IAM/storage/alert checks in `tests/infrastructure/recovery/recovery-contract.mjs`; browser health and accessibility checks in `apps/web/tests/`; and operational evidence in `docs/runbooks/library-recovery.md` plus `docs/operations/backup-recovery.md`. `tests/unit/Platform.Api.Foundation.Tests/MigrationChecks.cs` is the existing migration rehearsal seam. Existing `tests/version-control/recovery/RecoveryChecks.cs` only covers in-memory rewrite reachability and cannot serve as backup/restore evidence.
