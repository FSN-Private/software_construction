# Infrastructure validation

After `npm ci --ignore-scripts`, run `npm run validate` to typecheck, synthesize, assert the CloudFormation template, scan source for secret patterns, inspect the locked dependency tree, validate licenses, and query high-severity runtime vulnerabilities.

Synthesis writes only ignored `dist/` and `cdk.out/` files and performs no AWS deployment. The synth command fixes the non-production context; production and recovery inputs remain external bootstrap work.

## Temporary CDK security patch

[ADR-0013](../../docs/architecture/decisions/0013-temporary-patched-cdk-bundle.md) approves the local `vendor/aws-cdk-lib-2.267.0-brace-expansion-5.0.12.tgz` distribution while upstream CDK still bundles vulnerable `brace-expansion` 5.0.9. Only that bundled package is replaced; CDK's remaining file contents and Apache-2.0/MIT notices are preserved. `vendor/cdk-patch-provenance.json` records official npm input identities/integrities and the approved output checksum. `npm ci --ignore-scripts` installs the patched archive directly; no install script modifies dependencies. `npm run validate:vendor` checks its checksum, lockfile and actual installed version as part of normal validation. Audit and Trivy remain enabled.

To reproduce from the repository root, download official inputs into an ignored directory and rebuild:

```powershell
New-Item -ItemType Directory -Path artifacts/cdk-rebuild -Force
npm pack aws-cdk-lib@2.267.0 brace-expansion@5.0.12 --ignore-scripts --pack-destination artifacts/cdk-rebuild
python packages/infrastructure/scripts/rebuild-cdk-bundle.py artifacts/cdk-rebuild/aws-cdk-lib-2.267.0.tgz artifacts/cdk-rebuild/brace-expansion-5.0.12.tgz artifacts/cdk-rebuild/patched.tgz
```

The canonical archive was built with Python 3.14.7 and zlib `1.3.1.zlib-ng`. The procedure verifies input integrity, every unchanged CDK file, the exact replacement files and the output digest. Different compression implementations may produce different archive bytes; that fails the final checksum and requires review before replacing the approved artifact. To independently verify the checked-in contents without recompressing, use the same command with the vendor archive as output and `--verify-only`.

Remove this archive, provenance and rebuild/validation helpers when an upstream CDK release bundles a fixed version, after clean installation, synthesis/assertions, audit and Trivy pass. Restore an upstream registry dependency and its lockfile in the same change. The original vulnerable bundle is not a suitable security rollback.

For an authorized non-production bootstrap, pass real `ownerEmail`, `alertEmail`, `webOrigin`, `cognitoDomainPrefix`, `monthlyBudgetUsd`, and `deploymentRoleArn` contexts to `cdk diff` and `cdk deploy`, and write the deployment outputs with `--outputs-file`. The stack creates retained encrypted storage and PostgreSQL, immutable API/worker repositories, zero-count ECS bootstrap services, Cloud Map discovery, and an HTTPS API Gateway endpoint. It deliberately omits NAT gateways and load balancers from this low-budget environment; public-address Fargate tasks allow only VPC-link ingress to the API. After setting a permanent Cognito owner password, expose the output values to the protected GitHub environment with `scripts/configure-nonprod-github.ps1`; the script requires the owner username and password in process environment variables and never writes them to repository files.

The generated deployment role can describe, start, and stop only the generated RDS instance. `Deploy non-production` starts the database before migration. `Manage non-production lifecycle` starts or stops RDS and both ECS services manually, and its daily `17:00 UTC` schedule stops compute as a cost safety net. Both workflows serialize through `deploy-nonprod`; retained storage remains billable while compute is stopped.

Feature 012 adds an opt-in `exportTransport=true` context for native ZIP downloads through HTTPS CloudFront and an authenticated private ALB/VPC origin. Default bootstrap retains its existing budget topology. Supply the regional AWS-managed origin-facing prefix-list ID as `ExportCloudFrontPrefixListId`; keep API/web export capabilities disabled until the documented acceptance gates pass. The ALB has fixed cost even at zero ECS tasks and is not removed by the existing sleep workflow. Run `synth:exports` and `assert:exports` alongside bootstrap assertions; see [export operations](../../docs/operations/export-basket.md). These commands synthesize and validate templates without deployment.

## Feature 011 recovery infrastructure

Offline recovery synthesis is local-only and seeds deterministic placeholder values and availability zones. It does not perform lookups or represent deployable AWS identities:

```powershell
npm run synth:recovery
node ../../tests/infrastructure/recovery/recovery-contract.mjs
node ../../tests/infrastructure/recovery/verification-table-proposal.mjs
```

For a real two-account deployment, `recovery=true` requires `primaryAccountId`, `recoveryAccountId`, and `recoveryRegion`; the accounts must be distinct, and the regions are fixed to ap-southeast-1 and ap-southeast-2. The canonical `recoveryLibraryId` must match the provisioned library. Set `recoveryOwnerId` only when an owner/library pair must seed a canonical empty scope; capture and recovery discovery still enumerate every persisted scope.

Supply measured positive values for `recoveryMonthlyBudgetUsd`, `recoveryDatabaseInstanceType`, `recoveryDatabaseAllocatedStorageGiB`, `recoveryDatabaseMaxStorageGiB`, `recoveryWorkerEphemeralStorageGiB`, and `captureEphemeralStorageGiB`. Provide the deployed `primaryIngestBucketName`, `primaryKmsKeyArn`, and `captureDbSecretArn`, plus `recoveryAlertEmails`, `recoveryOwnerEmail`, and the existing foundation contexts (`ownerEmail`, `alertEmail`, `webOrigin`, `cognitoDomainPrefix`, `deploymentRoleArn`). `recoverySchedulesEnabled` must remain `false` until the documented seed and qualification checks pass.

Every recovery runtime digest is a required deployment input: `recoveryImageTag` is the full source revision; `recoveryImageDigest`, `recoveryApiImageDigest`, `recoveryIngestWorkerImageDigest`, and `recoveryRendererImageDigest` are immutable OCI manifest digests; `recoveryTemplateDigest` and `recoveryConfigurationDigest` are currently supplied as SHA-256 context strings; and `recoveryMigrationDigest` must equal the digest recomputed from the ordered migration filenames and exact SQL bytes included in the recovery-worker image. The app rejects a migration digest that differs from the repository migration artifacts. **Known release-binding blocker:** the template digest is injected into the same synthesized recovery template it is expected to identify, so the exact-template hash is self-referential. Do not use the offline placeholder or deploy/qualify this digest until a separately reviewed artifact-binding design resolves it without weakening independent verification. Pin the exact RDS CA bundle with `recoveryDatabaseRootCertificate` and `recoveryDatabaseRootCertificateSha256`; the latter hashes the full UTF-8 PEM bytes. Task code validates that same digest and uses PostgreSQL `verify-full`.

The signing and approval trust inputs are also required: `recoveryObservationSigningKeyId`, `recoveryObservationPublicKeySpkiBase64`, `recoveryObservationPublicKeySha256`, `recoveryOwnerApprovalKeyId`, `recoveryOwnerApprovalPublicKeySpkiBase64`, and `recoveryOwnerApprovalPublicKeySha256`. Fingerprints are computed over the decoded DER SubjectPublicKeyInfo bytes. The recovery owner approval role ARN and the separate MFA purge operator principal are `recoveryOwnerApprovalRoleArn` and `recoveryPurgeOperatorArn`; neither may be replaced with the other identity. Configure the exact repository and protected environment with `githubRepository` and `githubOidcSubject`.

Deploy the recovery stack with `recoveryStackOnly=true` and schedules disabled, review its outputs, then deploy the primary integration with schedules still disabled. The stack outputs include the copy, drill, isolated API, index-bootstrap, and protected GitHub drill task definitions, their role ARNs, and the separate MFA-gated purge CLI role ARN. The index-bootstrap role is a one-time ControlTable-only reader/writer; its manually invoked task has no source-reader, payload/evidence, database-secret, signer, fence, or purge permissions. Do not give the GitHub drill role permission to launch it or override the protected drill command. Use [the recovery runbook](../../docs/runbooks/library-recovery.md) for ordered deployment and qualification prerequisites.

The local synthesis command is not deployment authorization. Do not deploy these templates, enable schedules, run the bootstrap task, or execute recovery operations unless separately authorized for those external actions.

### Ordinary verifier publisher role proposal

[`policy-proposals/recovery-verifier-publisher.v1.json`](policy-proposals/recovery-verifier-publisher.v1.json) is a review-only task-role policy and runtime binding proposal. It is deliberately not imported by CDK and contains unresolved `__PLACEHOLDER__` values. It describes a separate `verify` task on a 15-minute schedule with the recovery PostgreSQL 18 secret and verify-full CA pins, all release digests, and the exact version, SHA-256, and byte length of `evidence/audit/genesis.v1.json`. Its only primary-account permission is `sqs:SendMessage` to the single recovery-observation queue; the drill role remains separate and has no primary-account permission. The separately retained `VerificationTable` is proposed for separate provisioning; local CDK does not create it or attach its verifier role pending exact authorization.

The proposal limits recovery reads to exact-version payload, snapshot, and point evidence; KMS decryption uses the regional S3 service and matching bucket-prefix encryption context. It strongly reads only the configured `OWNER#<scope hash>/INDEX` and exact latest membership row, then reads that point's copy pointer. It proposes bounded verification writes to a separate retained `VerificationTable` plus signing with the recovery evidence key. The JSON proposal specifies `pk`/`sk`, customer-managed encryption, point-in-time recovery, deletion protection, and `RETAIN`, but CDK does not provision the table and no task role is attached pending exact authorization. No owner-approval KMS action, object deletion, `Query`, `Scan`, role assumption, deployment permission, or queue receive permission is included. Run its static contract with `node tests/infrastructure/recovery/verifier-publisher-policy-proposal.mjs` and confirm the table remains absent after synthesis with `node tests/infrastructure/recovery/verification-table-proposal.mjs`.

The publisher proposal keeps the existing ControlTable read-only and puts verifier receipts, signed `POINT#<id>/AUDIT_VERIFY` proof envelopes, signed SQS outbox bodies, delivery state, and the audit head in `VerificationTable`. DynamoDB IAM `LeadingKeys` conditions constrain only the partition key; `dynamodb:Attributes` allowlists do not constrain the sort-key value. The separate table prevents a verifier write from overwriting ControlTable `COPY` pointers or owner-index rows, while the worker still must use exact `POINT#<id>/VERIFY`, `POINT#<id>/AUDIT_VERIFY`, and `OWNER#<scope hash>/VERIFIED` keys, immutable receipt bindings, and conditional delivery/audit-head updates. The role is not attached pending root review. The verifier and drill read the bounded latest sealed point from the configured owner/library index and exact `POINT#<id>/COPY`; routine verification does not enumerate history or fall back to `Scan`.

The policy proposal grants no task launch or schedule authority. The cross-region SQS network route, final task definition, and template-digest binding remain separate review items. The signed summary sent to SQS is limited to approved identifiers, digests, timestamps, class counts, and status codes; it must not contain media bytes, object locations, credentials, or raw errors.
